# 写提示词 / 整理需求

适用：把一段功能描述变成能直接实现的提示词，或评审一份已有的提示词。

## 骨架

```text
# 任务：<做什么> + 一句话目标
<给谁用、跑在什么之上>

## 硬约束（不可谈判）
- 平台 / 语言 / 版本 / 构建方式 / 运行形态
- 开箱即用必须满足的场景

## 行为清单（每条都能被看见）
1. <触发条件> → <可观察结果>
   反例：不要 <最常见的偷懒实现>
2. ...

## 机制选择（有明确取舍就写死）
- 用 X 而不是 Y，因为 Z

## 易错点（我踩过的）
- ...

## 交付物
- 产物、入口命令、目录结构

## 完成标准（逐条可验证）
- [ ] ...
```

## 六条硬要求

| 要求 | 反例 |
| --- | --- |
| 把「做好」换成**可观察现象**，并点名最常见的偷懒实现 | 「波形要好看」→「波形必须由实时 RMS 电平驱动，不要用写死的假动画」 |
| 参数前置，尺寸 / 时长 / 权重 / 阈值都写具体数值 | 「合适的圆角」「流畅的动画」 |
| 点到具体类或 API，不写「合适的组件」 | 「用合适的悬浮窗组件」→「NSPanel(nonactivatingPanel) + NSVisualEffectView(.hudWindow)」 |
| 每个机制配一句理由，且理由是**约束** | 「抑制 Fn 事件传递，否则会触发 emoji 选择器」 |
| 把踩过的坑写成需求 | 「API Key 输入框要能完全清空」「注入完成后恢复原剪贴板」 |
| 交付边界明确 | 「SPM 构建，Makefile 提供 build/run/install/clean，产物是签名的 .app」 |

## 自查

- [ ] 每处尺寸 / 时长 / 阈值都有具体数值
- [ ] 技术选型点名到类或 API，没有「合适的 X」
- [ ] 每个功能点至少覆盖一个失败场景（超时、授权被拒、能力不可用）
- [ ] 每个可配置项都有默认值，且默认值满足「开箱即用」
- [ ] 有可勾选的**完成标准**：每条能观察，或能跑一条命令验证
- [ ] **需求与设计分层标注**：需求不动的写死，口味参数（抖动幅度、弹性时长）交给实现方并说明可调；换掉设计不等于需求变更
- [ ] 逐句问「不写这句，模型会做出什么不同的选择」，答不上来的删掉

## 最容易漏的两条

**完成标准。** 需求写完不等于可验收：把每条需求翻译成能亲手执行的动作。「按住 Fn → 底部出现胶囊；松手 → 文字进输入框」「长按 Fn 不弹 emoji 面板」就是合格的样子。

**需求 vs 设计。** 「用哪个类、哪个 API」是设计；和需求写在同一层，之后任何替换都会被读成需求变更。要拆时走 `/skill:spec`（需求 → idea.md）→ `/skill:design`（机制取舍 → proposal.md），提示词只负责串成一次实现指令。（这是自研那条路，主流程见 `.agents/rules/dev-flow.md`。）
