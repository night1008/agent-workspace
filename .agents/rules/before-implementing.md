# 动手之前：对齐协议

像按返工计费的承包方那样工作：错误假设的成本是你的，多余提问的成本是我的。

适用：非平凡改动——新模块、新接口、schema 变更、迁移、auth、钱、删除。
改名、typo、20 行以内且只有一种正确写法的小改，直接做，不走这套。

## 1. 先自己查

代码、测试、配置、依赖清单先读。一分钟内能搜到的不是问题，是研究：测试框架、语言版本、lint 规则、错误处理惯例、目录结构、已有抽象，一律不用问。查到代码库自相矛盾，值得提。

## 2. 产出这四块，然后停下

**目标**：一段话复述我要什么，连同你拿来自检的验收标准。复述错了是最便宜的错误。

**阻塞问题（0–3 个）**：只有答错会导致整块返工才问，答错只是需要调整就不要问。每个问题都带上你的推荐默认值，让我能回一句「都按你说的」。没有阻塞问题就说没有、列 0 个。

**假设**：编号、具体、可证伪。「输入在 1 万行以内、能放进内存」是假设，「代码应该可维护」不是。触及哪块写哪块：

- 数据：形状、量级、可信度、编码、畸形输入长什么样
- 失败：超时 / 部分写入 / 下游 500 时怎么办——重试、报错、还是降级
- 边界：谁调用它、哪些是公开 API、有没有向后兼容义务
- 状态：并发、幂等、事务、顺序保证
- 环境：运行时版本、部署在哪、允许访问什么
- 范围：这次**不做**什么、留了什么 TODO
- 测试：哪些写测试、哪些不写

**方案**：要新增或修改的文件、关键函数与类型签名、动手顺序。在真实取舍处，一句话说明否掉的备选方案和理由。

然后等。别开始实现。

## 3. 批准之后

按批准的方案实现。中途发现某个假设错了、或方案经不起代码的现实，停下来说——不要悄悄换成另一个设计，也不要硬推一个你已经认为错的做法。

## 4. 收尾

设计与实现完成后做一个消融实验：确认新增的每一部分都在起作用。

完成标准：四块产出齐（目标 / 阻塞问题 / 假设 / 方案）→ 停住等批准 → 按批准实现 → 消融实验有结论。
